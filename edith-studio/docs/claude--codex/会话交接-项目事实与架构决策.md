> 给下一次接手 EDITH Studio 的 AI。本文记录稳定事实、已经确认的设计决策和后续方向。
> 压缩功能已经完成一次正式提交：`feat(studio): add slash commands and session compaction`。
> 如果后续会话继续修改压缩相关代码，仍然要先检查 `git status` 和 `git diff`，不要把未提交改动直接视为稳定事实。

## 一、项目事实与阅读入口

### 1. 产品是什么

EDITH Studio 是一个本地、单用户、面向 Coding Agent 的 Web 工作台：用户在某个项目目录启动 `edith`，一个本地 Go 进程服务这个目录，浏览器通过本地 HTTP/SSE 使用 Agent。

```text
启动目录 ProjectRoot
        ↓
一个 Studio 进程
        ↓
一个 Workspace
        ↓
会话、文件、模型、工具和 Agent 共同服务这个项目
```

不同项目目录的会话必须隔离。当前项目身份使用稳定的 `WorkspaceID`，作为框架 Session 的 `userID`：

```text
appName   = edith-studio
userID    = workspace:<规范化 ProjectRoot 的哈希>
sessionID = 一条对话的唯一 ID
```

### 3. 框架关键事实

1. tRPC Agent Go **不负责解析 Slash Command**。框架文档明确把 `/compact`、`/goal` 等命令交给应用层。
2. SessionService 提供摘要 API：
   - `CreateSessionSummary(ctx, sess, filterKey, force)`：同步生成并保存摘要；手动 `/compact` 使用 `force=true`。
   - `EnqueueSummaryJob(...)`：交给框架后台摘要 worker。
   - `GetSessionSummaryText(...)`：读取已经保存的摘要。
3. 框架提供 `summary.NewDynamicSummarizer`，可让长期 SessionService 根据当前请求 context 选择摘要模型，避免为了切换模型重建 SQLite Service。
4. `summary.WithContextThreshold(...)` 可以依据模型上下文窗口和比例触发摘要。模型的 `ContextWindow` 必须由产品模型模块提供给框架。
5. Agent 摘要相关选项的作用边界：
   - `WithAddSessionSummary(true)`：让下一次 Run 看到会话摘要；
   - `WithSessionSummaryInjectionMode(SessionSummaryInjectionUser)`：摘要放在系统指令和近期历史之间的用户内容位置；
   - `WithSyncSummaryIntraRun(true)`：长 ReAct Run 内在下一次模型调用前检查摘要；
   - `WithEnableContextCompaction(true)`：启用框架已有的工具结果压缩。
6. 首版不自行实现 tokenizer，不接各厂商 token 统计接口，也不增加 Token Tailoring。会话历史摘要加框架工具结果压缩已经足够。
7. Runner 的事件必须以 `IsRunnerCompletion()` 判断完整结束。浏览器断开后，后端仍继续消费事件并让 Runner 完成持久化收尾。

## 二、稳定的架构决策与代码偏好

### 1. 产品层与 Agent 核心层

```text
Web → Studio HTTP/SSE → Workspace 产品运行层 → Engine Agent 核心 → Runner
```

- `main` 只负责当前目录、根 Context、启动和退出；不组装模型、Runner、ToolSet 或 SQLite。
- `Workspace` 对应一个 ProjectRoot，是长期能力的汇合点；它创建、持有和关闭模块。
- `Engine` 只负责 Agent Run、取消、框架事件读取和稳定的 Studio StreamEvent；它不负责 Web、文件树、会话侧栏或 YAML 配置。
- `Studio` 只处理 HTTP 输入输出；不解析框架 Event，不承载业务策略。

### 2. Module 规则

Module 不是统一接口，而是具体包内真正有职责的结构体。只有存在长期资源、稳定状态或同时服务多个消费者时才创建 Module；简单能力用纯函数。

典型边界：

```text
workspace.Module   当前项目的长期产品运行层
engine             Agent 核心
project.Module     ProjectRoot 内的文件树和文件读取
session.Module     框架 SessionService、列表、历史、删除
models.Module      配置、模型实例、模型 Profile、供应商请求差异
tools              默认 Coding ToolSet 的注册函数
studio             本地 HTTP/SSE
```

Workspace 允许各模块汇合，但不为每个方法做无意义转发。一个模块需要给 Engine 的能力，就通过清晰的字段或依赖提供；需要注册 HTTP 的能力，就由 Studio 直接调用该模块的公开方法。

### 3. 配置、身份和生命周期

- 不设总 `config` 包；每个包自己读取自己的配置，配置类型放在该包的 `types.go`。
- `~/.edith/models.yaml` 是全局模型配置；`mcp.Module` 读取用户级 `~/.edith/mcp.json` 与项目级 `<ProjectRoot>/.edith/mcp.json`；Skills 等未来由各自模块读取。
- 配置包不依赖业务模块；Workspace 只拿已经解析好的能力。
- 谁创建资源，谁关闭资源；关闭顺序与依赖创建顺序相反。
- 不使用全局可变的当前项目、当前 Session 或当前 Run。

### 4. 流式事件和可读性

唯一事件主路径：

```text
Runner → frameworkEventCh → Engine 现场读取字段 → StreamEvent → SSE → Web
```

严格禁止：

- 额外 Event channel、事件桥、后台翻译 goroutine；
- `StreamTranslator` 之类的包装对象；
- 把文本、工具、状态分别藏进多个 `writeSSE...` 函数；
- 让 Studio 或 Web 直接认识框架 Event。

所有 channel 名称必须以 `Ch` 结尾。禁止泛名 `Open()`；使用 `New(Dependencies)`、`Load`、`Create`、`Start`、`Close` 表达真实动作。优先直白的 Go 代码，少嵌套、少抽象、少隐藏控制流。

## 三、已确认方案、当前进度与未来任务

### 1. 已经稳定完成的产品能力

- 本地 Studio 按启动目录工作，项目之间 Session 隔离。
- Workspace → Engine 的后端骨架已经建立。
- Runner 流式输出可转为稳定 StreamEvent，再通过 SSE 给 Web。
- Session 使用框架 SessionService + SQLite 保存；支持列表、读取和删除。
- Project API 按目录展开文件树，按点击读取文件，路径不能越出 ProjectRoot。
- Models 模块读取 `~/.edith/models.yaml`，启动时创建模型实例，并向 Web 返回不含密钥的模型目录。
- 模型 Profile 已包含 Provider、真实模型名、ContextWindow、Vision、Thinking Modes。
- Web 已有三栏工作台原型：会话列表、聊天区、文件树/代码区；模型和思考模式来自后端目录。
- 多模态图片输入已落地：仅 `vision=true` 模型可发图，前后端双重校验。
- MCP 扩展已落地：用户级与项目级 `mcp.json` 配置、三种传输、失败不致命、侧栏状态展示。
- Skills 已落地：系统/用户/项目三级目录发现、框架知识注入层（`skill_load` 等工具）、侧栏弹层交互、LoadMode session + 正文物化到 tool result；系统级内置技能 `//go:embed` + 每次启动 seed 到 `~/.edith/.system-skills/`。详见 §T 与 `docs/product/Skills系统设计指南.md`。
- 本机工具层改造（方案 c）已落地：claudecode 本地化到 `internal/claudecode`，`normalizePath` 放开 base_dir（文件工具全盘访问，可读写技能目录），bash 平台分派（Windows 指 Git Bash，避开 WSL 启动器）。详见 §U 与 `docs/product/工具集改造计划.md`。
- 子 Agent 已落地：父 Agent 经 AgentTool 委派框架内置只读探索者（`builtin.NewExplorer`），继承父工具面与模型、独立上下文执行；前端以 Agent Card 展示子过程，历史回放还原嵌套 agent 块。详见 §V 与 `docs/product/多Agent系统开发计划书.md`。
- 工具审批暂时删除，不保留半成品 Callback、权限 channel 或空包。

这些是架构和产品方向上的完成项；具体实现是否仍然通过测试，必须在接手时重新运行测试确认。

### 2. 已完成的首个功能：Slash Command 与会话压缩

已经确定采用 Workspace 命令层，而不是让 Engine 解析原始字符串：

```text
GET  /api/commands       → Web 获取命令目录
POST /api/commands       → Web 执行 Slash Command
                         → commands.Module
                         → Engine.Compact
                         → SessionService 摘要
```

当前首版只有 `/compact`，这条链路已经完成：

- `Definition` 只描述命令，不执行命令；字段是名称、说明、输入语法。
- 命令请求携带 `sessionId`、原始 `command`、当前 `modelId`、当前 `thinkingMode`。
- 未知命令、命令参数错误、模型选择错误由后端拒绝；不进入 Session，也不交给模型。
- `Engine.Compact` 只返回 `error`，不返回摘要全文。
- 手动压缩同步执行，成功返回小 JSON 状态；不使用 SSE。
- 压缩期间同一 Session 不能同时运行普通 Run。
- 自动摘要是隐藏的框架安全网，不产生前端事件；只有手动 `/compact` 显示成功状态。
- 当前模型选择通过 typed context 传给 DynamicSummarizer；不维护“Session 上次使用模型”的额外状态。
- 复用启动时创建的供应商实例；思考请求字段只做轻量请求适配，不重新建立网络连接。

本次提交还补充了以下压缩相关能力：

- 配置滚动摘要，让摘要可以随着会话继续增长而持续更新；
- 开启框架的工具结果上下文压缩，避免单个巨大工具结果占满模型请求；
- 固定父 Agent 使用的 Summary FilterKey，确保摘要创建和摘要读取使用同一个范围；
- 保留父 Agent 与未来 AgentTool 子 Agent 的 FilterKey 层级设计，不把未来子 Agent 的摘要混入父 Agent；
- 增加可读的模型 Prompt 日志，用于检查真正发送给 LLM 的上下文、摘要位置和工具结果压缩效果；
- 完善命令目录、模型配置和前端 Composer 的命令交互。

这一提交的核心事实是：

~~~text
/compact 不是把旧消息从数据库删除；
它调用框架 Session Summary API 生成派生摘要；
摘要保存后，下一次 Run 由框架读取摘要并组合近期历史；
原始 Session Event 仍然保留。
~~~

### 3. 接手后第一步

压缩功能已经完成，但接手新任务时仍然按以下顺序做，不要直接重写：

1. `git status --short`，确认哪些文件属于中间态。
2. 阅读本文、`docs/architecture/架构设计.md` 和 `docs/TODO.md`。
3. 用 CodeGraph/文档确认框架摘要 API，不凭旧记忆猜参数。
4. 检查 `/api/commands`、`/compact` 和 Prompt 日志的实际行为；如果发现回归，补测试和局部修复，不改变 Engine 的边界。
5. 运行 `go test ./...`、必要时 `go test -race ./...`，再做 Web 类型检查。
6. 只修复影响当前功能的错误；不要顺手重构已经确定的架构。

### 4. 后续产品优先级

压缩、上下文用量展示、图片输入、MCP、Skills、本机工具层（claudecode 本地化）和子 Agent（内置 Explorer + Agent Card）已经稳定进入基础能力，接下来按以下顺序推进：

1. 文件编辑、Diff、Agent 修改后的刷新策略。
2. 工具权限：重新设计成 Run 的暂停/恢复能力，不能再用 Callback + 事件桥临时拼接。
3. 分支、运行状态和更多 Web 产品能力。

> 更新（2026-08-07）：图片存储外置（ContentRef）已确认不做——本地单用户的 SQLite 撑得住图片，后期前端做图片压缩即可，不再列入优先级。

### 5. 交接时的沟通原则

用户最关心“这段代码具体做了什么”，不喜欢炫技、黑盒、泛化接口和隐藏 channel。解释新概念时先说目的，再说运行路径，最后说代码位置。遇到职责不明确时先问，不要私自发明一层抽象；能用一个清晰函数完成，就不要制造 Manager、Translator、Bridge 或通用 Registry。

# 附录：详细交接手册

以下内容不是新的架构规则，而是为了让下一次会话在没有完整历史上下文时，也能准确理解 EDITH Studio 的设计理由、运行边界和实现顺序。

## A. 用户的设计偏好

### A.1 用户希望看到什么

用户不是不理解复杂系统，而是不接受“代码看起来高级、但不知道具体在做什么”。讲解必须优先回答：

~~~text
这段代码的目的是什么？
谁调用它？
输入是什么？
输出是什么？
它持有什么长期资源？
失败时谁负责处理？
~~~

回答概念时建议采用以下顺序：

1. 先说它解决什么现实问题。
2. 再说它在 EDITH 中属于哪一层。
3. 再画一条从输入到输出的路径。
4. 最后才解释具体 API 或代码写法。

不要一上来介绍框架内部十几个接口，也不要把“框架提供了能力”说成“框架替我们完成了产品设计”。

### A.2 用户明确不喜欢的写法

- 为了“架构完整”预先创建没有真实逻辑的包。
- 为了“扩展性”先写通用接口、泛型 Registry、Manager、Bridge。
- 把一个直接函数拆成多层 Handler、Service、Translator、Adapter。
- 通过额外 channel 把本来能直接返回的值隐藏起来。
- 把输出藏在 writeSSEText、writeSSETool 等一堆函数中，让路由看不见实际返回值。
- 让 main 组装所有框架对象。
- 让 Engine 读取产品配置、文件系统或前端协议。
- 让框架 Event 类型直接穿透到 Web。
- 看到不确定的职责时直接自行发明方案。

### A.3 用户接受的复杂度

用户接受复杂度，但复杂度必须来自真实问题：

- Session 隔离需要稳定身份，允许有 WorkspaceID。
- 多家模型请求字段不同，允许 models.Module 做供应商字段适配。
- 框架 SessionService 需要长期持有，允许 session.Module 管生命周期。
- 浏览器断开后 Runner 仍需完成，允许 Engine 保留当前 Run 的状态。
- 文件路径必须限制在 ProjectRoot 内，允许 Project Module 做路径安全校验。

不允许为了未来可能出现的需求提前制造复杂度。

## B. EDITH Studio 的第一性原理

### B.1 产品存在的根本原因

普通 CLI Coding Agent 的问题是：

- 用户很难同时看清对话、工具调用和项目文件；
- 工具已经修改文件，但用户不知道修改了什么；
- 模型选择、思考程度、上下文使用量和权限状态分散在不同地方；
- 多轮会话不断增长，模型最终会遇到上下文限制。

EDITH Studio 的目标不是“把 CLI 搬到浏览器”，而是把 Coding Agent 的状态可视化：

~~~text
对话意图
  → 模型思考
    → 工具请求
      → 工具结果
        → 文件变化
          → 下一轮模型决策
~~~

因此，Web 是产品观察面，Engine 是执行内核，Workspace 是当前项目的长期世界。

### B.2 三种状态必须分开

#### 1. 产品状态

例如：

- 当前 Session；
- 左侧 Session 列表；
- 当前文件 Tab；
- 当前模型选择；
- 当前权限等级；
- 右侧文件树展开节点。

这些状态属于 Workspace 或 Web，不属于一次 Agent Run。

#### 2. Agent 运行状态

例如：

- 当前 requestID；
- 当前 Session 是否有 Run；
- 用户是否点击了停止；
- 当前框架 Event 是否完成；
- 当前工具调用是否已经开始。

这些状态属于 Engine 的短生命周期内存。

#### 3. 持久化状态

例如：

- Session Event；
- Session Summary；
- Session 更新时间；
- 未来的压缩元数据。

这些状态由框架 SessionService 负责，不能让 Web 自己持有一份事实。

### B.3 一个能力的判断方法

新增功能时，按以下问题判断所有者：

~~~text
它是否跨越多个 Run？
它是否需要 Close？
它是否给 Web 展示？
它是否只属于本次 Run？
它是否属于 Agent 决策本身？
它是否只是 HTTP 编码？
~~~

对应判断：

~~~text
跨 Run 的产品能力      → Workspace / Module
需要资源关闭            → 对应 Module
需要 Web 展示            → Module 导出产品读取能力 + Studio 路由
只属于当前执行          → Engine / Run
Agent 决策与模型调用    → Engine / Runner
HTTP 编码               → Studio
~~~

## C. 运行对象与生命周期

### C.1 进程级对象

~~~text
edith 进程
├─ root Context
├─ HTTP Server
├─ Workspace
│  ├─ Project Module
│  ├─ Session Module
│  ├─ Models Module
│  ├─ ToolSets
│  └─ Engine
└─ Web 请求处理
~~~

进程级对象启动一次，服务所有浏览器请求，但仍然只服务一个 ProjectRoot。

### C.2 Workspace 生命周期

~~~text
Create(ProjectRoot)
  → 规范化 ProjectRoot
  → 计算 WorkspaceID
  → 加载模型
  → 创建文件能力
  → 创建工具集
  → 创建 SessionService
  → 创建 Runner
  → 创建 Engine
  → 注册 Workspace 能力
~~~

关闭顺序必须反过来：

~~~text
停止接收新请求
  → 停止 HTTP Server
  → 关闭 Engine / Runner
  → 关闭 ToolSet
  → 关闭 SessionService
  → 进程退出
~~~

如果创建中途失败，已经创建的资源必须回收。没有成功构造完整 Workspace，就不能把半成品暴露给 Studio。

### C.3 Run 生命周期

~~~text
收到 RunInput
  → 校验 requestID/sessionID/message
  → 校验模型和思考模式
  → 申请 Session 运行权
  → 调用 Runner.Run
  → 消费 frameworkEventCh
  → 发送 StreamEvent
  → 看到 IsRunnerCompletion
  → 释放 Session 运行权
~~~

Run 不能保存到全局，也不能让下一次 Run 读取上一次 Run 的局部变量。需要跨 Run 保存的内容必须进入 SessionService 或明确的 Workspace Module。

## D. 后端包的详细合同

### D.1 cmd/edith

输入：

- 操作系统当前工作目录；
- 进程信号；
- 固定本地监听地址。

输出：

- 启动 Studio；
- 进程退出码；
- 启动失败日志。

它不应该出现以下内容：

~~~go
llmagent.New(...)
runner.NewRunner(...)
sqlite.NewService(...)
tools.NewToolSets(...)
~~~

这些属于 Workspace 组装范围。

### D.2 internal/studio

Studio 的 HTTP Handler 只做四件事：

1. 读取 URL、Header 和 JSON Body；
2. 调用 Workspace 的公开能力；
3. 把错误转换为 HTTP 状态码；
4. 把返回值写成 JSON 或 SSE。

路由函数应该能让人直接看见：

~~~text
输入 → 调用哪个能力 → 返回什么
~~~

Handler 不应该：

- 直接访问 SQLite；
- 直接调用模型；
- 直接读取项目文件；
- 直接判断框架 Event；
- 自己保存 Session 或 Run 状态。

### D.3 internal/workspace

Workspace 是“当前项目的组合根”，但不是“所有业务的垃圾桶”。

它应该只保存：

- 当前项目身份；
- 对外可用的长期模块；
- 创建和关闭这些模块的逻辑。

它不应该保存：

- Web 当前选中的文件；
- 某个请求的模型临时选项；
- 某条消息的 SSE 输出；
- 所有模块的重复转发方法。

### D.4 internal/engine

Engine 是最容易被污染的包，必须严格限制职责。

Engine 允许知道：

- Runner；
- 模型选择能力；
- SessionService；
- 工具集已组装结果；
- WorkspaceID；
- Run 的取消和完成状态。

Engine 不允许知道：

- HTTP Request/Response；
- SSE Header；
- React 组件；
- 文件树展开状态；
- Session 侧栏排序；
- YAML 文件路径；
- MCP JSON 的具体格式。

### D.5 internal/project

Project Module 只围绕 ProjectRoot 做文件能力。

文件读取规则：

~~~text
浏览器请求相对路径
  → 清理路径
  → 拼接 ProjectRoot
  → 解析最终路径
  → 验证仍在 ProjectRoot 内
  → 读取目录直接子项或单文件内容
~~~

禁止把浏览器提交的绝对路径直接交给 os.ReadFile。禁止让前端决定 ProjectRoot。ProjectRoot 在进程启动时确定。

### D.6 internal/session

Session Module 是框架 SessionService 的产品封装边界。

它负责：

- 创建 SQLite Service；
- 配置摘要器；
- 提供 Session 列表；
- 提供一条 Session 的聊天历史；
- 删除 Session；
- 提供给 Runner 的框架 Service；
- 关闭数据库资源。

它不负责：

- 决定前端卡片 CSS；
- 直接生成 SSE；
- 修改 Runner 的 Event；
- 把每条 Event 原样暴露给 Web。

### D.7 internal/models

Models Module 的核心不是“调用模型的函数”，而是“已经创建好的模型实例目录”。

产品层关注：

~~~text
模型 ID
供应商
真实模型名
上下文窗口
视觉能力
思考模式
~~~

框架层关注：

~~~text
model.Model
agent.RunOption
provider variant
request extra fields
~~~

Models Module 是两者之间的边界。它不应该把供应商请求字段散落到 Engine 或 Studio。

### D.8 internal/mcp

MCP Module 是用户级与项目级 MCP server 的产品封装边界。

它负责：

- 读取用户级 `~/.edith/mcp.json` 与项目级 `<ProjectRoot>/.edith/mcp.json`，项目级覆盖同名 server；
- 为每个 server 创建框架 MCP ToolSet，启动期 `Init` 预热；
- 把 stdio server 的 `env` 注入当前进程，子进程自动继承；
- 提供连接状态给 Studio / Web；单个 server 失败不阻塞启动；
- 导出连接成功的 ToolSet 给 Workspace 汇入 Agent；
- 关闭全部 MCP 连接。

它不负责：

- 读取框架 Event；
- 决定 server 的工具过滤策略（首版未做工具过滤）；
- 管理 MCP 多进程生命周期（仍属 §N 不应做的事）。

## E. 模型系统的稳定决策

### E.1 配置结构

模型配置采用“供应商连接信息”和“模型能力信息”分离：

~~~yaml
default: deepseek-pro

providers:
  deepseek:
    api_key: ...
    base_url: https://api.deepseek.com
    variant: deepseek

models:
  deepseek-pro:
    provider: deepseek
    name: deepseek-v4-pro
    context_window: 1000000
    vision: false
    thinking:
      default: max
      modes: [off, high, max]
~~~

API Key 只在后端内存使用，绝不返回给 Web。

### E.2 启动期和 Run 期

启动期：

- 读取 models.yaml；
- 校验全部 Provider 和 Model；
- 创建所有长期供应商实例；
- 生成可供 Web 使用的 Catalog。

Run 期：

- 根据 modelId 选择已注册模型；
- 根据 thinkingMode 生成框架请求选项；
- 根据模型 Profile 提供 ContextWindow；
- 不重新连接供应商。

因此，用户可以无感切换已注册模型，但修改 API Key、BaseURL 或新增模型仍需要重启，除非以后实现明确的配置重载能力。

### E.3 供应商差异

不同厂商的“思考程度”不能用一个框架字段简单概括。Models Module 负责转换：

~~~text
产品选择：thinkingMode = high
        ↓
Models Module 根据 provider
        ↓
thinking / reasoning_effort / enable_thinking 等请求字段
~~~

已调研并计划兼容的供应商/模型包括：

- DeepSeek：thinking enabled/disabled，部分模型有 reasoning_effort；
- MiMo：thinking.type enabled/disabled，无复杂档位；
- MiniMax M3：thinking adaptive/disabled，reasoning_split；
- GLM：thinking 加 reasoning_effort，产品层归并为少量有效档位；
- Kimi K3：始终思考，通过 reasoning_effort 调整强度。

模型能力 Profile 必须来自后端，不允许 Web 自己猜“这个模型支持视觉”或“这个模型有几个思考档位”。

## F. Session 摘要机制详解

### F.1 摘要解决什么问题

Session Event 会随着多轮对话增长。模型上下文窗口有限，旧的完整历史最终不能全部带入下一次请求。

摘要机制的目标不是删除历史，而是：

~~~text
旧的完整事件
  → 生成结构化摘要
  → 保存摘要记录
  → 下一次 Run 读取摘要 + 最近事件
~~~

原始 Session Event 仍然保存，摘要只是框架构造下一次模型请求时使用的压缩表示。

### F.2 自动摘要

自动摘要由框架根据条件触发：

- 新增事件数量；
- 新增 token 数量；
- 当前模型 ContextWindow 的比例；
- 时间条件。

EDITH 选择 ContextWindow 比例作为主要依据，因为不同模型上下文大小不同。模型的上下文窗口来自 models.yaml，不是前端填写。

自动摘要是隐藏的内部安全网：

- 不在聊天中追加一条“系统消息”；
- 不发送单独的 Web 事件；
- 不打断用户当前对话；
- 失败时记录错误，不破坏已有 Session 历史。

### F.3 手动 /compact

手动压缩是产品命令，不是普通模型消息：

~~~text
用户输入 /compact
  → Web 识别为命令入口
  → 后端重新解析和校验
  → Engine.Compact
  → CreateSessionSummary(force=true)
  → 摘要保存
  → 返回成功/失败 JSON
~~~

手动压缩使用本次 Composer 携带的 modelId 和 thinkingMode。这样不需要在 Session 中偷偷保存“最后模型”，也不会因为用户切换模型而使用错误的摘要器。

### F.4 DynamicSummarizer

长期 SessionService 只创建一次。动态摘要器在真正检查或生成摘要时读取当前请求 context：

~~~text
Engine.Run / Engine.Compact
  → models.WithSelection(ctx, selection)
  → SessionService
  → DynamicSummarizer
  → models.SummaryModel(selection)
~~~

SummaryModel 应复用启动时的基础模型实例。思考字段如果需要适配，只做内存层请求字段注入，不重新建立网络连接。

动态 resolver 必须轻量、确定、可重复调用。框架可能先检查一次是否需要摘要，再在真正生成时再次解析。

### F.5 摘要和工具压缩的关系

二者不是同一个功能：

~~~text
Session Summary
  压缩较早的会话历史

Tool Context Compaction
  压缩过大的工具结果
~~~

首版同时使用框架提供的两种能力，但不再自造第三套 Token Tailoring。不要在 EDITH 中实现自己的 token 计算器。

## G. Slash Command 详解

### G.1 为什么不放进 Engine

/compact 是用户输入语法，属于产品交互；Compact 才是 Agent 核心动作。

正确区分：

~~~text
“/compact”              → Commands Module 识别
“压缩 Session”           → Engine.Compact 执行
~~~

如果 Engine 接收原始字符串，后续 /help、/model、/session 等都会污染 Agent 核心。Engine 应该接收结构化输入。

### G.2 Definition 的意义

Definition 只是命令目录中的一项描述：

~~~text
Name        compact
Description 压缩当前会话上下文
Syntax      /compact
~~~

它用于：

- Web 输入 / 时显示建议；
- 未来显示命令帮助；
- 让后端成为命令目录的事实来源。

它不负责执行，也不应该保存 Engine 指针。

### G.3 命令执行规则

命令输入必须经过两层检查：

1. Web 可以提前判断输入是否以 / 开头，改善交互；
2. 后端必须再次解析，前端判断不能作为安全或正确性依据。

首版规则：

- /compact 合法；
- /COMPACT 可以归一化为 compact；
- 空字符串不是命令；
- 普通文本不是命令；
- /help 未实现，返回未知命令；
- /compact now 未实现参数，返回无效命令；
- 命令不写入 Session 历史。

### G.4 命令 API 的返回形式

命令不走 SSE，因为首版没有逐步展示摘要生成过程的需求。使用普通 JSON：

~~~json
{
  "command": "compact",
  "status": "completed"
}
~~~

不要把摘要全文返回给 Web。摘要的事实来源是 SessionService，前端只需要知道本次命令成功或失败。

## H. 流式事件协议详解

### H.1 StreamEvent 的角色

StreamEvent 是 EDITH 自己定义的 Web 协议，不是框架 Event 的别名。

框架 Event 面向 Runner 内部；StreamEvent 面向浏览器 UI。二者之间只允许在 Engine 的 Run 循环内直接转换。

### H.2 目前关注的事件类别

~~~text
run.started
reasoning.delta
message.delta
tool.started
tool.finished
run.error
run.canceled
run.completed
~~~

事件的顺序比单个字段更重要：

~~~text
run.started
  → reasoning.delta / message.delta
  → tool.started
  → tool.finished
  → 后续 reasoning.delta / message.delta
  → run.completed 或 run.error 或 run.canceled
~~~

### H.3 工具卡片边界

当前工具事件表示框架已经提出或执行了工具调用。审批机制暂时没有实现；未来如果加入审批，必须先解决 Run 暂停/恢复，而不是简单增加一个前端卡片事件。

### H.4 浏览器断开

浏览器的 SSE 连接断开，不等于用户取消 Agent。Engine 应停止向浏览器发送，但继续消费 frameworkEventCh，确保：

- Session 事件能保存；
- Runner 能完成内部清理；
- 工具资源能释放；
- Session 运行锁能释放。

只有用户明确调用 Cancel API，才记录为主动取消。

## I. Web 产品心智模型

### I.1 三栏布局

~~~text
左栏                         中栏                         右栏
────                         ────                         ────
当前 ProjectRoot              当前 Session 对话             文件树
Session 列表                  思考内容                       代码 Tab
新建/删除/切换                工具卡片                       只读编辑器
未来扩展/设置                 输入框和 Slash Command          后续 Diff
                              模型/思考/上下文状态
~~~

Session 列表只显示当前 WorkspaceID 的会话。右侧文件树直接对应当前 ProjectRoot，不需要用户再次上传或选择目录。

### I.2 后端事实优先

Web 可以保存交互状态，但不能猜测后端能力：

- 模型和思考模式来自 /api/models；
- Slash Command 来自 /api/commands；
- Session 列表来自 /api/sessions；
- 文件目录来自 /api/files；
- 当前运行事件来自 /api/runs SSE；
- 上下文使用量未来由后端返回。

前端不应该写死 deepseek-pro 的 ContextWindow，也不应该通过模型名称猜 Vision 能力。

### I.3 前端状态分层

页面至少需要区分：

~~~text
当前 Workspace：由后端启动目录决定
当前 Session：左栏选择
当前 Run：中栏提交后产生
当前文件 Tab：右栏页面状态
当前模型选择：Composer 状态，提交 Run/Command 时带入
~~~

不要让文件树展开导致 Composer 消失；不要让打开文件改变当前 Session；不要让加载 Session 历史覆盖右侧文件 Tab。

## K. 测试与验收矩阵

### K.1 Engine

- 空 RequestID、SessionID、Message 被拒绝；

### K.2 Session

- 不同 WorkspaceID 查询不到对方 Session；

- Context 取消能终止同步摘要。

### K.3 Slash Command

- GET /api/commands 返回命令目录；
- /compact 成功；
- 未知命令返回明确 4xx；
- 命令参数错误返回明确 4xx；

- 命令不产生用户消息和 Assistant 消息；

### K.4 Project

- 根目录能列出直接子项；
- 展开目录不会递归返回整个仓库；

- Thinking 默认值必须出现在 Modes 中；

### K.6 Web

- Web 类型检查通过；
- SSE 文本增量不会重复；
- 思考卡片和文本卡片边界正确；
- 工具卡片能从 started 进入 finished；

- Slash 建议来源于后端目录；
- /compact 成功/失败状态清楚显示。

## L. 常见误区与修复方式

### 误区一：把框架 Event 当成 Web 协议

修复：只在 Engine 里读取框架 Event，向 Studio 发送 StreamEvent。

### 误区二：把摘要模型固定成默认模型

修复：使用 NewDynamicSummarizer，从当前 Run/Command 的 typed context 解析模型。

### 误区三：让 /compact 走普通 Run

修复：Slash Command 是产品命令，走 /api/commands，内部调用 Engine.Compact。

### 误区四：让前端判断模型能力

修复：所有模型能力由 models.Module 读取配置后通过 API 返回。

### 误区五：为了支持未来命令，先做通用命令框架

修复：首版一个命令使用清晰的目录和 switch；只有命令数量真正增长后，才抽取重复结构。

### 误区六：Session 摘要直接覆盖原始历史

修复：摘要保存为框架 Session Summary；原始 Session Event 保留，下一次请求由框架组合摘要与近期历史。

### 误区七：压缩失败就清空会话

修复：摘要是派生数据。生成失败只能返回错误或记录日志，不能破坏原始事件。

### 误区八：浏览器断开就取消 Agent

修复：区分连接断开和用户主动 Cancel；Engine 继续消费事件完成 Runner 收尾。

### 误区九：把所有能力都放到 Workspace

修复：Workspace 只持有和组装；真实业务放在具体 Module，Agent 执行放在 Engine，HTTP 放在 Studio。

## M. 接手新功能时的固定工作流

每次实现功能，先写一页以内的计划，再动代码。

### M.1 第一步：确定所有者

写下：

~~~text
产品能力所有者：
Agent 能力所有者：
持久化所有者：
HTTP 路由所有者：
浏览器展示所有者：
~~~

如果一项功能出现两个“主要所有者”，先停止写代码，重新划边界。

### M.2 第二步：画最短路径

例如 /compact：

~~~text
Composer
  → POST /api/commands
  → Commands Module
  → Engine.Compact
  → SessionService
  → JSON status
~~~

不要在这张图里加入没有实际作用的 Manager、Service、Bridge 或额外 channel。

### M.3 第三步：查框架文档

只查这次功能直接依赖的框架 API。记录：

- 输入类型；
- 返回值；
- 是否同步；
- 是否持久化；
- Context 是否被传递；
- 失败时是否修改已有状态。

### M.4 第四步：先定义公共输入输出

输入输出类型必须靠近能力所在包。不要让 HTTP JSON 类型直接成为框架类型。

### M.5 第五步：实现最短可运行链路

先跑通一个真实请求，再补错误处理、并发和 Web 展示。不要先搭“完整框架”。

### M.6 第六步：审可读性

检查：

- 函数是否一屏内能看懂？
- 输入和输出是否在签名中清楚出现？
- 是否有一层只是转发？
- 是否能删掉一个接口或 channel？
- 资源创建和 Close 是否在同一可读范围？
- 错误是否保留了原始原因？
- 注释是否解释目的，而不是复述语法？

- MCP 多进程管理；

## P. 最近提交的压缩功能：实现事实补充

### P.1 提交身份

最近完成的提交主题是：

~~~text
feat(studio): add slash commands and session compaction
~~

它不是单纯增加一个 `/compact` 字符串判断，而是同时打通了四条链路：

~~~text
命令发现
  → 命令执行
    → Session Summary 持久化
      → 下一次 Run 读取摘要
~~~

同时，模型请求上下文现在可以通过 Prompt 日志检查，不再只能根据前端最终文字猜测模型实际收到了什么。

### P.2 滚动摘要的含义

滚动摘要不是每次都从零开始生成一段孤立文本，也不是简单截掉旧消息。它的产品含义是：

```text
本轮历史继续增长
  → 框架发现接近 ContextWindow 阈值
    → 读取当前摘要范围
      → 生成更新后的摘要
        → 使用同一个 FilterKey 保存
```

因此，下一次 Run 的上下文由两部分组成：

```text
稳定摘要
  +
摘要之后仍然需要保留的近期事件
```

如果未来发现摘要内容重复、顺序错乱或历史没有被正确裁剪，先检查 FilterKey 和框架的 Summary 注入逻辑，不要先在 Web 层手动删除消息。

### P.3 FilterKey 的设计

FilterKey 是摘要范围的身份，不是前端标签，也不是模型名称。

父 Agent 必须固定使用同一个父级 FilterKey：

```text
创建摘要时使用的 FilterKey
        ==
读取摘要时使用的 FilterKey
```

如果创建和读取使用不同的 FilterKey，会出现以下假象：

- `/compact` 看起来成功，但下一次 Run 仍然读不到摘要；
- 数据库里有摘要记录，但模型上下文没有变化；
- 自动摘要和手动摘要各自生成两份互不相干的内容。

未来 AgentTool 子 Agent 需要独立摘要范围时，采用父子层级：

```text
parent filter key
├─ child A filter key
└─ child B filter key
```

子 Agent 的摘要不能被父 Agent 误读。当前版本只实现父 Agent，子 Agent 只保留层级设计，不提前实现子任务逻辑。

### P.4 当前模型与摘要模型

普通 Run 的模型选择来自 Composer：

```text
modelId + thinkingMode
```

这两个字段会进入当前请求的 typed context。DynamicSummarizer 从 context 解析选择，再向 Models Module 请求对应的摘要模型能力。

这条设计解决了三个问题：

1. 用户切换模型后，摘要不会一直使用启动时的默认模型；
2. SessionService 不需要因为换模型而重新创建 SQLite 连接；
3. Web 不需要维护“这个 Session 上次使用了哪个模型”的隐藏状态。

模型实例仍然是启动期创建的长期能力。摘要请求所需的 thinking 字段只做轻量请求适配，不能在每次压缩时重新建立供应商连接。

### P.5 工具结果上下文压缩

工具结果和普通聊天历史是两类数据：

```text
用户消息 / Assistant 回复 / 工具调用历史
  → Session Summary

单次工具返回的大块输出
  → Context Compaction
```

工具结果压缩的目的，是避免一个 `find`、日志、构建输出或大文件结果占满当前模型请求。它不负责决定 Session 的长期摘要内容。

首版使用框架提供的工具结果压缩，不添加自定义 Token Tailoring。遇到工具上下文问题时，先检查：

- 是否开启了框架工具压缩；
- 工具结果是否被正确标记；
- Session Summary 和 Tool Compaction 是否使用了错误的范围；
- Prompt 日志中的最终请求是否仍然超过 ContextWindow。

### P.6 Prompt 日志的使用方式

Prompt 日志的目的是验证事实，而不是把模型内部思考暴露给用户界面。调试压缩问题时，重点看：

```text
当前模型是谁？
当前 ContextWindow 是多少？
摘要是否已经注入？
摘要位于 System 和近期历史之间吗？
旧事件是否被压缩？
工具结果是否被裁剪？
当前请求是否重复携带了旧摘要？
```

日志检查顺序：

1. 先看请求使用的模型和思考模式；
2. 再看摘要是否存在；
3. 再看摘要与近期事件的顺序；
4. 最后看工具结果是否压缩。

Prompt 日志可能包含用户代码、文件内容和模型上下文，只适合开发调试。未来必须增加日志级别、敏感内容处理和生产环境关闭策略，不能默认永久打印完整 Prompt。

### P.7 压缩失败的处理原则

摘要是派生数据，不是原始 Session 的唯一副本。压缩失败时：

```text
保留原始 Session Event
  → 返回命令失败
    → 不删除历史
      → 下一次仍可重试
```

可能的失败原因包括：

- 当前模型 API 失败；
- Context 取消；
- Summary FilterKey 错误；
- Session 不存在；
- 摘要内容无法保存；
- 模型请求仍超过上下文限制。

排查时不要直接删除 sessions.db，也不要为了“让页面恢复”清空 Session。先读取错误链和 Prompt 日志，确认失败发生在生成、保存还是读取阶段。

### P.8 压缩功能的回归检查

以后修改 Run、Models、Session 或 Web Composer 时，至少手动验证：

~~~text
1. 发送一条普通消息，确认正常流式输出。
2. 切换到另一模型，确认普通 Run 使用新模型。
3. 执行 /compact，确认命令成功且不产生聊天消息。
4. 再发送一条消息，确认 Prompt 中存在摘要和近期历史。
5. 让工具返回较大结果，确认工具上下文压缩仍生效。
6. 在压缩期间取消请求，确认原始 Session 没有损坏。
7. 换一个 ProjectRoot，确认看不到原项目的 Session。
~~~

## Q. 交接结论更新

压缩功能现在不再属于“未来计划”，而是 EDITH Studio 的基础运行能力之一：

```text

### S.1 提交身份

### S.2 配置与覆盖

- 用户级 `~/.edith/mcp.json` + 项目级 `<ProjectRoot>/.edith/mcp.json`；项目级覆盖同名 server（整体替换，不做字段级 merge），不同名叠加。
- 配置文件不存在或为空文件都视为无配置；文件存在但语法错误（含未知字段）会启动失败并提示，属于配置错误。

### S.3 框架能力与连接

- 使用 `mcp.NewMCPToolSet(conn, WithName(name))`，一个 server 一个 ToolSet；`Init(ctx)` 启动期预热（initialize + tools/list）。
- 三种传输：stdio（command/args）、sse / streamable_http（serverUrl/headers）。
- 工具名前缀：`WithName(serverName)` → 模型侧工具名 `{server}_{tool}`，前端工具卡片直接显示该名。
- stdio 的 `env` 字段：框架不支持在配置里透传，EDITH 启动时注入当前进程环境，子进程自动继承（副作用：同进程其他子进程也可见，进程退出即消失）。
- 框架默认 MCP 协议版本 `2025-03-26`，兼容只支持 2025-06-18 及之前的 server（如麦当劳 MCP）。

### S.4 失败不致命与状态

- 单个 server 连接失败只记录 `error` 状态，不阻塞其他 server 或 Studio 启动；`GET /api/mcp` 返回 `[{name, transport, status, toolCount, error}]`。
- 失败 server 不挂到 Agent；修改配置后重启生效（与 models.yaml 一致）。
- 侧栏「扩展 · MCP」区显示 server 列表、状态点（connected 绿 / error 红）与工具数；error 状态悬停看错误信息。

### S.5 代码组织与职责

```text
internal/mcp/
├─ types.go     Config、ServerConfig、ServerStatus（对外状态类型）
├─ config.go    Load()：读用户级+项目级 mcp.json、合并、空文件视为无配置
└─ module.go    Module：建 ToolSet、Init、env 注入、状态、Close

Workspace：创建 mcp.Module，把 ToolSets() 汇入 llmagent.WithToolSets
           （MCP ToolSet 不放 workspace.toolSets，避免双重关闭）
Studio：GET /api/mcp 只编码状态
Engine：无感知，MCP 工具就是普通 ToolSet 工具
```

### S.6 已确认边界

- stdio env 是进程级注入，跨 server 可见（本地单用户可接受）。
- 首版不做：运行时热加载、工具动态刷新（`WithRefreshToolSetsOnRun`）、per-request header、mcpbroker、工具过滤。
- MCP 多进程管理仍属「当前不应做」（见 §N）。

## V. 子 Agent 接入：实现事实补充

### V.1 提交身份

```text
4680d1c feat(studio): 接入子 Agent 展示层，内置 Explorer 经 AgentTool 委派 / add sub-agent display layer with builtin Explorer delegation
```

设计文档：`docs/product/多Agent系统开发计划书.md`（含框架 6 种方案筛选、前后端双路径 dual-verify 验证、落地后的实测修复）。

### V.2 决策与执行机制

- **执行机制 = AgentTool（同步委派）**：`tool/agent` 的 `agenttool.NewTool` 把子 Agent 包装成普通工具，父 Agent 调用、等结果继续推理。语义同 Claude Code Task，是 Coding 委托的正解。经筛选弃用：`transfer_to_agent`（路由移交，父不汇总）、`team`（协调者/交接链，EDITH 父 Agent 即协调者）、`taskrun`（后台任务，第二形态）。
- **子 Agent = 框架内置 `builtin.NewExplorer`**（只读探索者）：name=`explorer`、description/instruction 现成；默认继承父工具面（claudecode 全工具 + MCP + skills）与模型；只读是**软约束**（instruction 提示），非权限隔离。
- **装配点**：`tools.NewAgentTool()` 一行返回 `tool.Tool`，配 `WithStreamInner(true)`（子事件透传）+ `WithPinModel(true)`（清掉父继承的 ModelName，消除 `deepseek-flash not found` 降级 WARN）。

### V.3 数据契约与展示

- **子事件判据统一**：`ParentMetadata != nil`（框架契约：顶层事件为 nil，子事件必有）。**不用 author 判据**——子调用会合成 author="user" 的事件会搅混；author 只当显示名。
- **StreamEvent 加两个字段**：`author`（空=父，非空=子名）+ `parentToolCallId`（= 父 `ParentMetadata.TriggerID`）。前端用 author 归组、parentToolCallId 精确关联到对应 Agent Card（避免并行串卡）。
- **前端 Agent Card**：`AssistantBlock` 联合类型加递归 `agent` 变体（id/name/arguments/status/result/blocks）。父 tool.started(explorer) 先建 tool 卡，第一条子事件把它升级为 agent 卡（同 id 状态连续）；子事件按 author 进 blocks；父 tool.finished 填 result 终态。渲染分支放兜底 tool 分支之前，递归自身。
- **历史还原**：`messagesFromEvents` 预扫描所有子事件的 `ParentMetadata.TriggerID` 收集 agent 调用 ID（数据驱动、不硬编码工具名），还原时父 tool_calls 打开 agent 块 → 子事件进嵌套 Blocks → 父 tool.response 关闭填 result。

### V.4 代码组织

```text

internal/workspace/workspace.go       删内联，一行 tools.NewAgentTool() 挂父 Agent WithTools
internal/engine/types.go              StreamEvent 加 author + parentToolCallId
internal/engine/run.go                读 ParentMetadata 判子事件；块状态按 author 重置（子文本不续父 block ID）
internal/session/types.go             AssistantBlock 加嵌套 Blocks
internal/session/history.go           messagesFromEvents 还原嵌套 agent 块（预扫描 agentCallIDs）
web/src/lib/stream.ts                 StreamEvent.author/parentToolCallId；AssistantBlock 递归 agent 变体
web/src/features/chat/apply-event.ts  父/子路由 + tool→agent 升级 + agent 关闭

```

### V.5 已确认边界

- 只读是软约束：Explorer 继承父写工具（write/edit/bash），靠 instruction 提示不修改；硬只读（`builtin.WithToolFilter` 滤掉写工具）留待需要时收紧。
- 单层单子、无并行：子事件精确关联靠 parentToolCallId；并行多 explorer 路由留待二期。
- 无独立 run id / 不可后台管理：AgentTool 是同步调用；taskrun 后台任务留待第二形态。
- 不做：文件定义体系（`.edith/agents/`）、多角色（reviewer/worker）、用户手动触发 UI、分支树。
- 子 Agent 模型 = 父当前选择（WithPinModel 只清 ModelName 覆盖，实际仍用父模型实例）。
- 已知实测修复：历史还原先开 agent 块导致思考被挤到 explorer 卡下方（顺序与实时不一致）——已改为先追加父思考/文本、再开 agent 块。
