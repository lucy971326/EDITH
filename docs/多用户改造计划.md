# Agent Demo 多用户改造计划

## 1. 当前目标

在暂不实现登录注册、暂不实现用户自定义 Bot/App 的前提下，把系统从“代码写死单用户”改成“开发版支持多个 user_id”。

目标是先消除 `u-alice` 硬编码，不提前引入复杂的多租户、认证和配置中心。

## 2. 必须遵守的隔离边界

Runner 的隔离范围始终是：

```text
AppName + user_id + session_id
```

- `AppName`：当前固定为 `demo-app`
- `user_id`：用户身份标识
- `session_id`：用户的一条会话

不能把隔离简化成只有 `session_id`，也不能跨用户复用同一个 `user_id`。

## 3. 第一阶段：Web 支持手动填写 user_id

### 前端

- 在聊天页面增加 `user_id` 输入框。
- 使用 `localStorage` 保存用户填写的值。
- 页面加载时恢复上次填写的 `user_id`。
- `/stream`、会话列表、会话历史统一使用同一个 `user_id`。
- 移除所有 `u-alice` 硬编码。

### 后端

- `POST /stream` 校验 `user_id` 非空。
- `GET /sessions` 校验 `user_id` 非空。
- `GET /sessions/{sessionID}` 校验 `user_id` 非空。
- 继续把请求中的 `user_id` 传给 Runner。

### 阶段边界

前端手填的 `user_id` 只是开发阶段的用户标识，不是身份认证。任何人都可以填写其他用户的 ID，因此暂不用于真实生产环境。

## 4. 第二阶段：IM 使用平台用户 ID

### Telegram

从消息的 `from.id` 生成用户标识：

```text
user_id = telegram:<from.id>
session_id = telegram:dm:<chat.id>
```

不再使用 `u-alice`。

### 飞书

从事件发送者 ID 生成用户标识：

```text
user_id = feishu:<sender_id>
session_id = feishu:dm:<chat_id>
```

### 说明

第一阶段 Web 的手动 `user_id` 与第二阶段 IM 自动生成的 `user_id` 暂时不要求互通。后续登录或绑定流程建立映射后，再让 Web 和 IM 进入同一个内部用户。

## 5. 暂时不做的内容

- 登录注册。
- 真正的用户认证与授权。
- 用户自定义 Telegram Bot。
- 用户自定义飞书 App。
- 多 Bot / 多 App 管理。
- 凭证数据库与密钥管理。
- 组织、团队、角色、RBAC。
- GitHub 账号绑定。
- 修改 Runner、Gateway、Session、Memory、Sandbox 的核心隔离机制。

## 6. 改动范围

预计只修改：

```text
Agent专用/web/app/chat/page.tsx
Agent专用/trpc-agent-go-demo/main.go
Agent专用/trpc-agent-go-demo/channel/telegram.go
Agent专用/trpc-agent-go-demo/channel/feishu.go
```

预计不修改：

```text
gateway/gateway.go
Runner
Session Service
Memory Service
Sandbox Provider
Next.js stream BFF
```

## 7. 验证标准

- Web 用户 A 和用户 B 使用相同 `session_id` 时，Session 仍然隔离。
- Web 切换 `user_id` 后，只能看到对应用户的会话列表。
- Telegram 不再进入 `u-alice` 的 Session。
- 飞书不再进入 `u-alice` 的 Session。
- 相同用户、相同 `session_id` 可以继续恢复历史。
- 空 `user_id` 请求被后端拒绝。

## 8. 后续演进方向

第一阶段稳定后，再单独设计：

```text
登录用户
  ↓
内部 user_id
  ↓
Telegram from.id / 飞书 sender_id / GitHub user.id
```

之后再考虑用户自带 Bot/App、凭证加密和多平台绑定。
