# 定时任务设计

## 结论

- 定时任务走 Gateway 统一入口，与 Web/IM 同构
- cronAdapter 进程内调用 Gateway，复用 IncomingMessage 契约
- 任务定义存 cron_jobs 表；不需要执行记录表，也不需要状态机
- 运行真相源 = ManagedRunner，结果真相源 = 会话历史，下次触发真相源 = next_run_at

## 1. 表结构（cron_jobs）

```text
cron_jobs
  ├── id
  ├── clerk_user_id    ← 身份，绝不能少
  ├── name             ← 任务名（前端填表定义）
  ├── task_type        ← once / recurring
  ├── schedule         ← 标准 cron 表达式
  ├── prompt           ← 任务指令
  ├── enabled          ← 用户开关
  ├── next_run_at      ← 调度器扫描依据
  ├── running          ← 防重叠锁（0/1）
  └── created_at
```

### 时区（方案 A：用户属性）

时区不是任务的属性，是用户的属性。存 user_agents.timezone（当前缺失，需新增，默认 Asia/Shanghai），cron_jobs 不存时区：

```text
user_agents
  ├── user_id
  ├── personality
  ├── default_model_id
  └── timezone          ← 新增，默认 ''（兜底 Asia/Shanghai）
```

调度器计算 next_run_at 时，按该用户的时区解释 cron 表达式。未来 IM、通知、历史时间显示复用同一字段，不重复存储。

### 为什么不需要状态机

三个真相源各管一摊，谁也不重复：

```text
运行真相  → ManagedRunner（requestID 查询/取消）
结果真相  → 会话历史（cron:job_id 的 session，打开即可见）
下次真相  → cron_jobs.next_run_at
```

执行记录（跑过几次、成功失败）都能从会话历史查出来，单独建表就是重复存储。

### 为什么保留 task_type

schedule 只回答"什么时候跑"，回答不了"跑完这次还有没有下次"：

- 周期性任务：执行完 → 算下次 next_run_at
- 一次性任务：执行完 → next_run_at = NULL，enabled = false

调度器必须有一个明确依据来决策，这个依据就是 task_type。

## 2. 调度器

数据库轮询，不挂 per-task goroutine：

```text
每 5 秒：
  SELECT * FROM cron_jobs
  WHERE enabled = 1 AND next_run_at <= now AND running = 0
  → 原子抢占（见下）
  → 触发 cronAdapter
  → 执行完根据 task_type 更新 next_run_at / 关闭任务
```

原子抢占防重叠、防多实例双跑：

```sql
UPDATE cron_jobs
SET next_run_at = <下次时间>, running = 1
WHERE id = ? AND enabled = 1 AND next_run_at <= now AND running = 0
-- 影响行数 = 1 才算抢到
```

任务收尾（RunStream 结束事件）时把 running 置回 0。

## 3. cronAdapter（执行器）

与 WebAdapter 对称，进程内调用 Gateway：

```go
gateway.IncomingMessage{
    Channel:        "cron",
    ExternalUserID: clerkUserID,   // 直接就是 Clerk 用户 ID
    SessionKey:     "cron:" + jobID, // 同一任务固定，天然防重叠 + 历史可聚合
    RequestID:      uuid,          // 与 RunStatus/Cancel 对上
    Message:        job.Prompt,
    ImageIDs:       nil,
    ModelID:        "",            // 走用户默认模型兜底
}
```

### 信任渠道

Gateway.resolveMessage 对非 web 渠道会查绑定表；cron 是平台内部发起，ExternalUserID 已是 Clerk 用户 ID，必须跳过绑定查询：

```go
var trustedChannels = map[string]bool{
    "web":  true,
    "cron": true,
}

// resolveMessage 中
if !trustedChannels[input.Channel] {
    // 才查绑定表
}
```

## 4. 结果展示

不需要额外存结果：用户点开 cron:job_id 对应的会话页面即可看到执行结果。

## 5. 创建方式

两种并存：

- Web 表单手动创建：填 name / schedule / prompt；时区由浏览器自动带出、可修改，写入 user_agents.timezone
- Agent Tool 对话创建：封装"插入 cron_jobs 记录"为工具，Agent 从自然语言生成 cron 表达式

Tool 创建注意三点：
- cron 表达式入库前必须校验合法性
- 时区从 userconfig 拿（user_agents.timezone），兜底 Asia/Shanghai；Web 表单创建时前端可用浏览器时区自动带出
- clerk_user_id 从当前 run 上下文取，不信 Agent 传入
