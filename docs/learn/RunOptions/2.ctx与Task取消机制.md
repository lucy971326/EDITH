# ctx 与 Task 取消机制

> 复习笔记。回答两个问题：ctx 在 Go 层面是什么？任务有几种取消方式？

---

## 一、ctx 是什么

**ctx = context.Context = "可取消 + 可超时 + 可携带请求数据"的请求级作用域**。

Go 没有 Task struct、没有状态机，但有三个原语把"任务生命周期管理"下沉到了语言层面：

| 原语 | 作用 |
|---|---|
| `goroutine` | 后台执行 |
| `channel` | 数据/信号传递 |
| `context` | 取消传播 + 超时 + 值透传 |

**ctx 是其中负责"取消传播"的那个**——父 ctx 取消，所有下游子 ctx 自动取消。

---

## 二、ctx 的四个动作

### 1. 创建根 ctx

```go
ctx := context.Background()  // 永不取消，整个进程最长寿
```

### 2. 派生可取消 ctx

```go
ctx, cancel := context.WithCancel(parent)
defer cancel()  // 习惯：defer 释放资源
```

### 3. 派生超时 ctx

```go
ctx, cancel := context.WithTimeout(parent, 30*time.Second)
defer cancel()  // 超时也会自动 cancel
```

### 4. 携带值

```go
type ctxKey string
const userIDKey ctxKey = "userID"

ctx := context.WithValue(parent, userIDKey, "alice")

// 下游函数
uid := ctx.Value(userIDKey).(string)  // "alice"
```

**纪律**：`WithValue` 只用于跨 API 边界传递请求元数据，不传业务参数。

---

## 三、ctx 的传播规则

```
ctx 派生树（树形结构）
parent (Background)
   │
   ├── child1 (WithCancel)   ← parent 取消 → child 自动取消
   │     │
   │     └── grandchild       ← parent 取消 → grandchild 自动取消
   │
   └── child2 (WithTimeout 30s)
```

**核心规则**：
- **父死子亡**：parent cancel → 所有下游 ctx 自动 cancel
- **子死父不亡**：child cancel → parent 不受影响
- **截止时间继承**：parent 的 deadline 会传给 child

---

## 四、ctx 取消的传播（核心）

```go
ctx, cancel := context.WithCancel(context.Background())

go func() {
    select {
    case <-ctx.Done():       // ★ 关键：ctx 取消时这个 channel 关闭
        fmt.Println("stopped:", ctx.Err())  // context canceled
        return
    case <-time.After(5 * time.Second):
        fmt.Println("done")
    }
}()

time.Sleep(1 * time.Second)
cancel()  // ★ 一秒后取消，goroutine 的 ctx.Done() 收到信号
```

**心智模型**：`ctx.Done()` 是"取消通知 channel"——任何用 ctx 的 goroutine 都该监听它。

---

## 五、取消 Run 的几种方式（语言层 + 框架层）

### 方式 A：HTTP ctx 直接传

**最简单**——HTTP request 自带 ctx，断开自动取消。

```go
eventCh, _ := r.Run(req.Context(), userID, sessionID, msg)
// 用户关浏览器 → req.Context() 取消 → Run 跟着死
```

**优点**：零成本，前端断开链路全自动。  
**缺点**：取消只能由"传 ctx 的人"控制，外部无法主动停。

---

### 方式 B：自己建 ctx + cancel

**ctx 派生 + cancel 函数持有**——脱离 HTTP 控制。

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

// goroutine 里跑
eventCh, _ := r.Run(ctx, userID, sessionID, msg)

// 另一处调 cancel() 即可停 Run
```

**适用**：
- 想给 Run 加超时
- 想从其他 goroutine 主动停
- 想脱离 HTTP ctx 控制

---

### 方式 C：DetachedCancel + 自己的 cancel

**Run 跟任何外部 ctx 解耦**——内部用自己的 ctx 边界。

```go
// Run 内部用 context.Background() 派生，不会被外部 ctx 拖死
eventCh, _ := r.Run(parentCtx, userID, sessionID, msg,
    agent.WithDetachedCancel(true),
    agent.WithMaxRunDuration(5 * time.Minute),  // ★ Run 自己有硬截止
)

// parentCtx 取消不影响 Run
// 但 Run 仍受 MaxRunDuration 限制
```

**适用**：HTTP 立刻返回 + Run 后台跑完的场景。

---

### 方式 D：按 requestID 取消（ManagedRunner）

**Run 的 cancel 托管给 Runner**——任何 goroutine 按 ID 都能停。

```go
requestID := uuid.NewString()
eventCh, _ := r.Run(ctx, userID, sessionID, msg,
    agent.WithRequestID(requestID),
)

// 任意 goroutine：
mr := r.(runner.ManagedRunner)
mr.Cancel(requestID)
```

**适用**：运维检测超时、配额耗尽、用户主动停止、多 Run 协调。

---

## 六、四种方式对比

| 方式 | 谁持有 cancel | 谁能停 Run | 适用场景 |
|---|---|---|---|
| A. HTTP ctx | HTTP runtime | 只能 HTTP 断开 | 用户在线看 SSE |
| B. 自己 ctx | 当前 goroutine | 自己调 cancel() | 加超时/主动取消 |
| C. DetachedCancel | Runner 内部 | 只能超时 | 后台任务模式 |
| D. requestID | Runner | 任何 goroutine | 集中控制平面 |

---

## 七、兼容性最好的方案

**B + D 组合**——前者负责"链路自动取消"，后者负责"跨边界主动取消"。

```go
// 框架建议的"通用模式"
// 1. 启动 Run
requestID := uuid.NewString()
ctx, cancel := context.WithCancel(parentCtx)
defer cancel()

eventCh, _ := r.Run(ctx, userID, sessionID, msg,
    agent.WithRequestID(requestID),  // ★ 启用方式 D
)

// 2. 注册到集中控制平面（可选）
registerToControlPlane(requestID, cancel)

// 3. 启动 drain goroutine（防 channel 阻塞）
go func() {
    for range eventCh {
    }
}()

// 4. 当需要停止时（任一触发）：
cancel()                                  // 方式 B
mr := r.(runner.ManagedRunner); mr.Cancel(requestID)  // 方式 D
```

**为什么这种组合兼容性最好**：

| 触发方 | 用哪个 |
|---|---|
| 前端断开 | parentCtx 取消（B 链） |
| 配额系统 | `mr.Cancel(reqID)`（D） |
| 运维 cron | `mr.Cancel(reqID)`（D） |
| Run 自己超时 | `WithMaxRunDuration`（D 的另一种形态） |
| 父 Run 取消子 Run | `mr.Cancel(reqID)`（D） |

**一条链路**（HTTP ctx）+ **一个集中控制平面**（requestID）——所有取消场景都有解。

## 八、EDITH 现状分析

**当前取消链路**：
```
前端 signal
   ↓
BFF signal 转发
   ↓
Go req.Context()
   ↓
r.Run(req.Context(), ...)
```

**当前用的是方式 A**——前端断 → 全链断。

**够用吗**：用户在线 SSE 场景 ✓，运维/配额场景 ✗。

**forward/ 阶段建议**：

1. **保留方式 A**——零成本，不动
2. **加一个 helper 函数**——为方式 D 铺路
3. **暂时不引入 CancellationPlane**——等真有运维/配额需求再写

```go
// forward/internal/runopt/cancel.go
func MakeRunCtx(parent context.Context, reqID string) (context.Context, context.CancelFunc, []agent.RunOption) {
    ctx, cancel := context.WithCancel(parent)
    return ctx, cancel, []agent.RunOption{
        agent.WithRequestID(reqID),
    }
}
```

**未来扩成 CancellationPlane 时，这个 helper 不变**——只是把 cancel 存进 map。

---

## 九、一句话

> **ctx 是"取消传播通道"**。
> **取消方式：A 跟 HTTP 走 / B 自己建 ctx / C Run 跟父解耦 / D 按 ID 集中取消**。
> **兼容性最好的方案：B + D 组合**——既保留 HTTP 链路的自动取消，又支持运维 / 配额的主动取消。
