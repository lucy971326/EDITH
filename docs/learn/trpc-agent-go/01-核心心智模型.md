# 01 - 核心心智模型

> 看框架就看两样：**接口（能干什么）** + **结构体（需要什么）**。

---

## 1. 理解法

```go
// 接口 = 契约（能做什么）
type Runner interface {
    Run(ctx, userID, sessionID, message) (<-chan *Event, error)
}

// 结构体 = 依赖（需要什么才能跑起来）
type runner struct {
    appName         string
    agents          map[string]agent.Agent
    sessionService  session.Service  // ← 需要一个 Session 服务
    pluginManager   agent.PluginManager
    // ...
}
```

**三条公理**：
1. 接口方法签名一致，实现可以完全不同（FunctionTool / MCP Tool / AgentTool 都是 `Call()`）
2. 一个结构体只要方法签名匹配，自动实现接口（Go 没有 `implements`）
3. 对扩展开放，对修改关闭：加新能力 = 写新结构体实现接口

---

## 2. 六大核心概念总览

| 概念 | 接口 | 主要实现 | 何时用 |
|---|---|---|---|
| **Runner** | `Runner` | `runner` | 业务代码唯一入口 |
| **Agent** | `agent.Agent` | `LLMAgent` / `ChainAgent` / `ParallelAgent` / `CycleAgent` / `GraphAgent` | 定义"能干什么" |
| **Model** | `model.Model` | `openai.Model` / `anthropic.Model` | 调 LLM |
| **Event** | 无接口（纯数据） | `event.Event`（嵌入 `*model.Response`） | 数据流载体 |
| **Tool** | `tool.Tool` / `CallableTool` / `StreamableTool` | `FunctionTool` / `MCP Tool` / `AgentTool` | 给 Agent 加能力 |
| **Plugin** | `plugin.Plugin` | 8 个内置 + 自定义 | 全局拦截 |

## 3. 数据流（Event 是核心）

```
Runner.Run(ctx, userID, sessionID, msg)
   │
   ├─ 组装 Invocation（Agent + Session + Model + Message + RunOptions）
   │
   ├─ Agent.Run(invocation) → 启动后台 goroutine
   │
   └─ 返回 <-chan *event.Event
        │
        ▼ 业务代码消费
        for ev := range eventCh {
            // ev 是 *event.Event
            ev.Response.Choices[0].Delta.Content  // 流式 chunk
            ev.Response.Choices[0].Message.Content // 完整消息
            ev.IsRunnerCompletion()                // 整次结束
        }
```

**Event 关键字段**：
```go
type Event struct {
    *model.Response             // 嵌入 LLM 响应
    RequestID     string        // 本次 Run 的 ID
    InvocationID  string        // Invocation ID
    ParentInvocationID string   // 多 Agent 调用链
    Author        string        // 事件发起者（Agent 名）
    Branch        string        // 多 Agent 调用链路径
    Tag           string        // 业务标签（如 transfer / code_execution）
    StateDelta    map[string][]byte  // 状态增量
}
```

**事件类型（`Object` 字段）**：
- `chat.completion.chunk` — 流式输出
- `chat.completion` — 完整回复
- `tool.response` — 工具结果
- `agent.transfer` — Agent 转移
- `runner.completion` — Runner 结束
- `error` — 错误

### Event 字段速记卡（最容易踩坑的部分）

**心智模型**：
```
Event = 邮件信封
  Response = 信封本身（状态/时间/用量）
    Choices[0] = 信纸
      Message = 完整版（一次性写完）
      Delta   = 流式草稿（边写边发）
```

**按场景查字段**：

| 想拿 | 看哪里 |
|---|---|
| 流式打字效果 | `Choice.Delta.Content`（每个 chunk 都有） |
| 完整回复（非流式） | `Choice.Message.Content` |
| 模型决定调工具 | `Choice.Message.ToolCalls`（**不是 Delta**） |
| 工具执行结果 | `Choice.Message.Role == "tool"` + `ToolID`/`ToolName`/`Content` |
| 配对工具调用 | `ToolCall.ID == ToolResponse.ToolID` |
| 模型思考（DeepSeek） | `Choice.Delta.ReasoningContent`（仅流式） |
| Token 用量 | `Response.Usage`（最后 chunk 才有） |
| 跑完没 | `Event.IsRunnerCompletion()`（唯一可靠结束） |

**三条黄金法则**：

1. **文本永远走 Delta**（流式下 Message.Content 是空的）
2. **工具调用永远走 Message**（Delta.ToolCalls 是分块的，不能直接用）
3. **工具结果是另一个 Choice**，靠 `ToolID == ToolCall.ID` 配对

**最易混淆对比**：

| 这个 | 不是这个 |
|---|---|
| `Event.IsRunnerCompletion()` | `Response.IsFinalResponse()`（当前回复 ≠ 整次 Run） |
| `Choice.Message.ToolCalls` | `Choice.Delta.ToolCalls`（增量，要拼接） |
| `Message.Role == "tool"` | `Message.ToolID == ""`（没 ID 不算工具结果） |
| `Response.Done` | `Event.Done`（不同层同名） |

**万能调试打印**：

```go
log.Printf("ev: obj=%s done=%v partial=%v choices=%d toolcalls=%d",
    ev.Object, ev.Done, ev.Response.IsPartial,
    len(ev.Response.Choices),
    len(ev.Response.Choices[0].Message.ToolCalls),
)
```

**官方推荐循环**（agent.md 原文）：

```go
for ev := range eventCh {
    if ev.Error != nil { ... }
    if ev.IsRunnerCompletion() { break }
    if len(ev.Response.Choices) > 0 {
        if content := ev.Response.Choices[0].Delta.Content; content != "" {
            fmt.Print(content)
        }
    }
}
```

## 4. 执行流程（一次 Run 内部）

```
Runner.Run()
  │
  ├─ ① getOrCreateSession() ────── sessionService.Get/CreateSession
  │
  ├─ ② appendIncomingMessage() ─── AppendEvent（用户输入）
  │
  ├─ ③ Agent.RunWithPlugins()
  │    │
  │    ├─ Plugin 层 BeforeAgent
  │    ├─ Agent 层 BeforeAgent
  │    ├─ flow.Run() ← LLM 循环
  │    │    ├─ Plugin 层 BeforeModel ──┐
  │    │    ├─ Model.GenerateContent   │  ← 双层回调
  │    │    ├─ Plugin 层 AfterModel  ──┘
  │    │    ├─ Tool 执行
  │    │    │    ├─ BeforeTool（可短路）
  │    │    │    ├─ Tool.Call()
  │    │    │    └─ AfterTool（可覆盖结果）
  │    │    └─ ... 循环直到 LLM 返回无 tool_call
  │    │
  │    └─ Agent 层 AfterAgent
  │
  ├─ ④ 事件循环：persistEvent + Plugins.OnEvent
  │
  └─ ⑤ AppendEvent(runner.completion) ──── 最终完成事件
```

**关键规则**：
- 只有 `!IsPartial && IsValidContent()` 才写 Session（Partial chunk 不持久化）
- Plugin 双层：Runner 级 → Run 级 → Agent 自身回调
- 业务代码只看到一条事件流，不需要关心底层

---

## 5. "事件流"的本质

整个框架的异步通信都建立在 `<-chan *event.Event` 上：

| 谁产生 | 谁消费 | 用途 |
|---|---|---|
| Model | Agent | LLM 流式输出 |
| Agent | Runner | Agent 执行结果 |
| Runner | 业务代码 / AG-UI | 完整事件流 |
| AG-UI Translator | AG-UI 客户端 | 转前端协议 |

**好处**：所有异步逻辑统一一个抽象，业务代码只需要 `for ev := range ch`。

---

## 6. 并发控制要点

| 层级 | 机制 |
|---|---|
| Runner 同一 requestID | `runs map[string]*runHandle` 防重复 |
| AG-UI 同一 SessionKey | `running map[session.Key]` 防并发，重复返回 409 |
| Session 写 | `stateWriteMu`（SQLite）/ `stateMu`（InMemory）串行化 |
| 流式 chunk | channel buffer（默认 512，可调） |

---

## 7. "Rules" 没有一等公民

框架不给"Rules"抽象，给的是组合原语：

| 需求 | 用什么 |
|---|---|
| 稳定全局约束 | `WithGlobalInstruction()` / `WithInstruction()` |
| 单次请求背景上下文（历史前） | `agent.WithInjectedContextMessages(...)` |
| 单次请求动态约束（贴近用户） | `agent.WithLateContextMessages(...)` |
| 完全控制消息序列 | `BeforeModel` 回调重写 `request.Messages` |

**经验**：用 Late Context + role=user 注入动态约束，role=system 中间插可能不兼容。
