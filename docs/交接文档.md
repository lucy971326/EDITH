# EDITH 项目交接文档

> 给下一位开发者或 AI 的项目地图。先读本文建立全局心智模型，再按文末路径进入细节。
>
> 最重要的要求：**可读性优先。状态只放在流程真正发生的地方；不要为了封装制造额外状态对象。**
>
> 本文只记录当前上下文和关键决策；RunOptions、格式、代码风格的完整规则以
> [`AIKNOW/`](AIKNOW/) 和 [`learn/RunOptions/`](learn/RunOptions/) 中的专题文档为准。

## 1. 项目现在是什么

EDITH 是一个多用户的服务端 Agent 应用。

```text
浏览器（web-v1）
  → Next.js BFF（鉴权、转发、浏览器 API）
  → Go Runtime（backend-v1：装配本次 Agent Run）
  → tRPC-Agent-Go Runner（模型、工具循环、Session、事件流）
  → 模型 / MCP / Sandbox / SQLite
```

当前主线是 `web-v1 → backend-v1`。根目录的旧 `web/`、`backend/` 是 1.0 之前的实现，只能作为参考，不能把旧代码原样搬回新架构。

一句话理解核心：

```text
一个长期共享的 Runner
  + 每次请求临时组装 RunOptions
  + Runner.Run 返回 eventCh
  + Web 将 eventCh 直接转为 SSE
```

## 2. 三个核心事实

| 名称 | 它解决什么 | 不要误解成什么 |
|---|---|---|
| `Session` | 一段会话的最终历史事实 | 不是浏览器内存里的临时 UI 状态 |
| `eventCh` | 一次 Agent Run 的运行事件流 | 不是最终聊天记录 |
| `agent_runs` | 一次任务的 Token 用量与审计账本 | 不是 Run 控制面或新的复杂任务系统 |

前端最终都显示为 Timeline UI，但来源有两个：

```text
正在生成：SSE 实时补充 Timeline
生成结束或恢复后：从 Session 历史加载完整 Timeline
```

因此不要试图给 SSE 分片做“断点回放”。断线恢复的权威来源是 Session 历史。完整格式见
[`AIKNOW/05-格式约束.md`](AIKNOW/05-格式约束.md)。

## 3. 运行与渠道的边界

模型是否流式，和渠道不是一件事。

```text
Web 渠道：消费 eventCh，实时输出 SSE
未来 IM 渠道：消费同一条 eventCh，收集完成后发送一张完整消息卡片
```

不要为 Web 和 IM 创建两套 Agent / Runner。渠道差异只是一次 Run 的输出策略，用户差异则通过 RunOptions 传入。完整方针见
[`AIKNOW/02-EDITH-RunOptions-方针.md`](AIKNOW/02-EDITH-RunOptions-方针.md)。

## 4. 必须保持的运行模型

### 长期共享的能力

`Runner`、`LLMAgent`、共享 Model、SQLite、E2B client 等，在进程启动时组装一次，供所有用户使用。

它们不保存某个用户的 API Key、Prompt、MCP 工具、当前会话或当前请求数据。

### 每次 Run 的数据和资源

`ctx`、`userID`、`sessionID`、消息、用户配置快照、RunOptions、MCP ToolSet、Usage 都只属于本次调用。

主流程应该始终可以从 `backend-v1/internal/webapi/agentrun.go` 自上而下读懂：

```text
接收请求
  → 创建 task ctx
  → 读取本次用户运行配置
  → 加载本次 MCP 等临时资源
  → 组装 RunOptions
  → Runner.Run 得到 eventCh
  → 逐个读取 Event：记录 usage、转 SSE、收尾
```

如果新增代码让这条线藏进 `Builder`、`Manager`、状态结构体的一串方法里，先停下来重新设计。完整的判断标准见
[`AIKNOW/04-codestyle.md`](AIKNOW/04-codestyle.md)。

## 5. Web 断线恢复：已完成的决定

这是当前稳定性工作的核心，下面的边界不能混淆。

### 5.1 浏览器断线不等于取消任务

HTTP/SSE 连接只负责让用户实时观看。Go 会使用独立的 `task ctx` 执行 Agent Run；SSE 写入失败后停止向浏览器写，但仍继续消费 `eventCh`，让模型、工具、Session、MCP 资源和 Usage 正常结束。

原因很简单：用户只是断网，并没有表达“停止任务”的业务意图。

### 5.2 `requestId` 是一次任务的身份

浏览器在发送前用 `crypto.randomUUID()` 生成 `requestId`，并将 `{ requestId, sessionId }` 写入 `sessionStorage`。

它有三件事：

- 幂等键：同一 `requestId` 只允许启动一次 Run，网络重试不会创建重复任务；
- 活跃状态查询键：浏览器通过 `ManagedRunner.RunStatus` 查任务是否仍在运行；
- 取消键：用户主动停止已通过 `ManagedRunner.Cancel` 实现；配额和运维中止将复用它。

Go 只接收、校验和持久化这个 ID；不要改为由 Go 生成。

### 5.3 恢复方式

```text
SSE 断开 / 页面刷新
  → 浏览器读取 sessionStorage 中的 pending run
  → 轮询 GET /api/agent-runs/{requestId}
  → running：显示“任务仍在后台执行”提示
  → 404：ManagedRunner 已不再管理该 Run，重新请求会话历史
  → 用 Session 的完整 Timeline 恢复页面
```

`ManagedRunner` 是活跃 Run 的控制面真相源：`RunStatus(requestId)` 存在表示仍在执行，
`Cancel(requestId)` 发送取消信号。取消接口返回 204 只表示 Runner 已接受该信号；前端必须
继续轮询到 404，才能确认 Run 已结束。Go 会通过 Runner 中 `SessionKey.UserID` 与 BFF
注入的可信 userID 比较，确保用户只能查询或取消自己的 Run；不匹配同样返回 404。

这个提示只属于“浏览器不再实时观看、任务仍在运行”的状态；正常在线 SSE 期间不应出现。

### 5.4 Timeline 的单一写入者规则

同一会话存在本地 SSE 时，只有 SSE 可以写该会话的 Timeline；历史加载请求不能覆盖它。

否则用户切到别的会话再切回来时，较慢返回的旧历史会把实时分片或最终结果覆盖掉。`chat-page.tsx` 用页面内的 `liveStreamSessionIDs` 明确记录这个所有权。

## 7. 明确还没做的事

- **运行时上限 / 配额中止**：有明确业务规则后，再让 task ctx 负责超时或取消。
- **同一会话并发 Run 的产品规则**：是否禁用发送、排队或允许并行，需要和取消交互一起设计。
- **IM 渠道适配**：预留渠道位置，但目前只实现 Web；IM 将消费同一 `eventCh` 并在完成后发送整张卡片。
- **EDITH 自有 Skills 系统**：尚未实现，不要把旧研究内容当作现有能力。

不要因为这些未来需求，提前创建 Task Manager、状态机、Builder 或多个 Service。真实规则出现时，直接在现有清晰主链上扩展。

## 8. 代码风格：这是硬约束

- 一次性的线性流程，用普通函数和局部变量。
- `if err != nil` 单独写；不要与下一步合并成一行。
- 纯数据直接用结构体字面量或 `var`；没有实际初始化工作的 `NewXxx` 不要写。
- 不要为了“面向对象”给一个结构体配很多小方法，例如 `stream.Started()`、`stream.Add()` 这类会隐藏数据流的 API。
- 谁创建资源，谁在同一个可读范围内关闭它。MCP ToolSet 必须在完整消费 eventCh 后关闭。
- 共享对象只保存长期能力；请求数据显式通过函数参数传递。
- 先让主运行链一眼可读，再考虑抽取。抽取只能减少真实复杂度，不能把复杂度藏起来。

## 10. 修改前的最后检查

```text
这个东西是长期共享能力，还是本次 Run 的临时数据？
这段代码是否让 eventCh 的消费路径更清晰？
浏览器断开和用户主动取消，是否仍被明确区分？
是否会让历史响应覆盖正在进行的 SSE？
资源是谁创建、谁关闭，代码里是否一眼可见？
是否真的需要新对象，还是一个直接函数更清楚？
```

如果无法明确回答，先不要写抽象，回到主流程重新画出数据流和生命周期。
