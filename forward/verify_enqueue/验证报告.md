> **验证日期**: 2026-07-13

> **运行命令**: `go run ./forward/verify_enqueue/main.go`

## 验证目标

**同一 Session 运行期间追加消息，能否进入当前 Run、AG-UI 事件流和历史。**

Session 正在运行 → 调用 `Core Runner.EnqueueUserMessage(requestID, message)` → 消息在安全边界进入当前 Run → Agent 读取消息并继续 → SSE 与 `/history` 能正确展示。

## 关键设计

### requestID 映射

AG-UI Runner 默认不会把它的 `runID` 传给 Core Runner 作为 `requestID`。通过自定义 `runOptionResolver` 确保映射：

```go
aguirunner.WithRunOptionResolver(func(ctx context.Context, input *adapter.RunAgentInput) ([]agent.RunOption, error) {
    return []agent.RunOption{
        agent.WithRequestID(input.RunID),  // AG-UI runID → Core Runner requestID
    }, nil
})
```

### 阻塞 Tool 控制

`blockingTool` 使用两个 channel：
- `started` — 关闭时通知主 goroutine Tool 已开始执行
- `release` — 关闭时 Tool 返回结果

不依赖任何 sleep。

## 已验证结论

1. **✅ `EnqueueUserMessage` 能在 Run 运行中成功追加消息到当前 Run** — 返回 nil，不创建第二个 Run
2. **✅ Agent 在下一次模型调用时能读取追加消息** — Mock Model 第二次调用消息列表包含补充要求
3. **✅ 追加消息出现在 tool_call/tool_result 完整结束之后** — 消息顺序正确
4. **✅ 同一条 SSE 流能收到追加消息后的后续事件** — 没有断开连接
5. **✅ Run 只出现一次 RUN_STARTED 和一次 RUN_FINISHED** — 没有第二个 Run
6. **✅ Session Events 完整保存包括追加消息在内的全部事件** — 5 条事件，顺序正确
7. **✅ AG-UI Track Events 全部属于同一个 runID** — 10 条 track events，全部 runID=enqueue-run-1
8. **✅ MessagesSnapshot 包含追加消息及其后续回复** — 4 条消息，最后一条引用补充要求
9. **✅ 错误边界：Run 完成后 EnqueueUserMessage 正确拒绝** — 返回错误

## 尚未验证的假设

1. **Web 端实时 SSE 展示** — 只验证了服务端 SSE 事件流正确，未验证前端 AG-UI 框架消费
2. **多个追加消息（连续 Enqueue）** — 只验证了单次追加
3. **工具超时场景** — Tool 卡死 + EnqueueUserMessage 后的行为
4. **并发 EnqueueUserMessage** — 多个 goroutine 同时调用的行为
5. **跨 Session 隔离** — 同一个 Core Runner 不同 Session 的 EnqueueUserMessage 互不干扰
6. **真实 LLM 模型下的端到端验证** — 本次使用 Mock Model

## 是否需要修改框架

**不需要修改框架。** 框架的 API 已完整支持：

- `runner.EnqueueUserMessage(r, requestID, message)` 直接可用
- AG-UI Runner 通过 `WithRunOptionResolver` 映射 runID → requestID
- Tracker 自动记录追加消息对应的 AG-UI 事件

**EDITH 接入建议：** 保持 `RunRouter` 维护的 `session_key → requestID` 映射，在追加消息时直接用已知的 `requestID` 调用 `EnqueueUserMessage`。
