## 7. 对照说明：为什么上次 `verify_enqueue` 没有看到追加消息

**两次实验的实际行为一致**——追加用户消息在 MessagesSnapshot 中都存在。但第一次实验的解析代码有 bug：

1. 使用了错误的 struct 类型解析 MESSAGES_SNAPSHOT 事件，导致 `json.Unmarshal` 失败，事件被静默丢弃
2. 没有打印 HTTP status 和原始响应体，无法诊断问题
3. 没有检查 MESSAGES_SNAPSHOT 事件数量，当事件数为 0 时直接误判为"历史缺失"

本次修复后，确认 `/history` 正确返回了包含追加消息的 MESSAGES_SNAPSHOT。

## 8. 架构问题最终回答

> **Q: EDITH 是否可以不修改 AG-UI 框架，仅使用 RunRouter + Core Runner.EnqueueUserMessage 实现连续消息？**

**A: 可以。** ✅

实验证明：

| 能力 | 结果 |
|------|------|
| 追加消息进入 Core Run | ✅ 模型第二次调用看到 `role=user content="补充要求：请同时添加测试"` |
| 追加消息出现在 SSE 实时流 | ✅ `TEXT_MESSAGE_START role=user` + CONTENT delta |
| 追加消息写入 Session Events | ✅ `session_events[3].content == "补充要求：请同时添加测试"` |
| 追加消息出现在 MessagesSnapshot | ✅ `role=user, content精确匹配, count=1` |
| 追加消息的 Track Event | ✅ 有 TEXT_MESSAGE 类型的 track 事件 |
| Run 结束后幽灵防护 | ✅ 返回 error，无幽灵消息 |

**不需要添加 framework.patch。** 框架现有的 Core Runner `EnqueueUserMessage` + AG-UI Runner 原生 Tracker 机制已经能让追加消息正确进入 MessagesSnapshot。

注意：无框架补丁时，Track 中的追加消息是 `TEXT_MESSAGE` 类型而非 `CUSTOM user_message`。但这不影响 MessagesSnapshot 的展示。两种类型的 track 事件在 reduce 后都正确映射为 `role=user`。
