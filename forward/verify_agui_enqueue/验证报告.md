## 一、框架原有能力调查

### 关键发现

| 查询项 | 回答 | 来源 |
|--------|------|------|
| 1. AG-UI Runner 是否有公开的追加消息 API？ | **没有**。`Runner` 接口只有 `Run()` 方法 | `server/agui/runner/runner.go:54` |
| 2. 是否有 Hook/Callback 可记录额外用户消息？ | **没有公开回调**。`recordUserMessage` 是私有方法 | `server/agui/runner/runner.go:914` |
| 3. `ConcurrentMessageStreamsEnabled` 是否与 Steering 有关？ | **无关**。仅控制多 message stream 并发 | `server/agui/runner/options.go:333` |
| 4. Session TrackService 是否可以安全写入 AG-UI Track？ | **可以**。`tracker.AppendEvent(ctx, key, event)` 是公开方法 | `server/agui/internal/track/tracker.go:34` |
| 5. AG-UI Runner 创建初始 user_message TrackEvent 的位置？ | `recordUserMessage()` 在 `server/agui/runner/runner.go:914-933`，使用 `aguievents.NewCustomEvent(multimodal.CustomEventNameUserMessage, ...)` | `server/agui/runner/runner.go:928` |
| 6. 已有 `Canceler` 模式可借鉴？ | **有**。`Canceler` 是独立扩展接口，`runner` 结构体实现它 | `server/agui/runner/cancel.go:34` |

### 能否不修改框架源码完成？

**不能。** AG-UI Runner 没有公开的 Steering 入口。Core Runner 有 `EnqueueUserMessage`，但无法写入 AG-UI Tracker。最小改动是新增一个 `SteerableRunner` 扩展接口，让 `runner` 结构体实现它。

### 缺少的最小接口

一个公开方法，签名约：

```go
EnqueueUserMessage(ctx context.Context, input *EnqueueUserMessageInput) error
```

该方法需要访问 `runner` 结构体的私有字段：`runAppName`/`appNameResolver`、`userIDResolver`、`tracker`、`runner`（Core Runner）。

## 二、原型新增能力

### SteerableRunner 接口

```go
type SteerableRunner interface {
    Runner
    EnqueueUserMessage(ctx context.Context, input *EnqueueUserMessageInput) error
}
```

### EnqueueUserMessageInput

```go
type EnqueueUserMessageInput struct {
    ThreadID string        `json:"threadId"`  // Session ID
    RunID    string        `json:"runId"`     // Core Runner requestID
    Message  types.Message `json:"message"`   // AG-UI 用户消息
}
```

### 实现流程

```go
EnqueueUserMessage(input)
    ↓
1. 解析 appName / userID（复用 resolveAppName / userIDResolver）
    ↓
2. 构建 session.Key
    ↓
3. 转换 types.Message → model.Message
    ↓
4. Core Runner.EnqueueUserMessage(requestID, msg)  ← 关键路径
    ↓ 成功
5. recordUserMessage(key, msg)  ← 写入 AG-UI TrackEvent（尽力而为）
    ↓
返回 nil
```

### 顺序与事务性

| 场景 | 行为 |
|------|------|
| Core Enqueue 成功，Track 写入失败 | Core 已入队无法回滚。记录 warning，**返回 nil** |
| Core Enqueue 失败 | 不写 Track，直接返回 Core 的错误 |
| Tracker 为 nil | Core 仍执行，记录 warning |

## 八、是否值得向框架贡献该接口

**值得，但需要先解决以下问题：**

### 值得的理由

1. 接口遵循已有 `Canceler` 模式，对框架的侵入最小
2. 复用 runner 内部分辨器（`resolveAppName`、`userIDResolver`），避免业务侧重复解析逻辑
3. 验证了 Core Enqueue + Track 写入两阶段事务的核心路径
4. 不破坏现有 Runner 接口兼容性

### 建议的改进点

1. **去除 MessagesSnapshot 中追加用户消息的重复显示**。当前 `recordUserMessage` 写入的 CUSTOM 事件和框架自动生成的 TEXT_MESSAGE 事件在 reduce 后出现重复。可以为 CUSTOM user_message 和后续 TEXT_MESSAGE 建立关联 ID，在 reduce 阶段去重。

2. **添加 `steer.consumed` 消息回执到 SSE 流**。框架已自动生成 `ACTIVITY_SNAPSHOT` 类型的 `steer.consumed` 事件，这是一个很好的设计，前端可以据此判断追加消息已被 Agent 处理。

3. **两阶段失败时的操作可能考虑**。当前设计是 "Core 优先"，Track 失败只记录 warning。对于要求强一致性的场景，可能需要异步补偿机制或重试。

4. **允许指定 userMessage.Name**。当前 `recordUserMessage` 会自动填充 `Name = key.UserID`，对于多用户场景可能不够灵活。
